Homework (Simulation)
This program, x86.py, allows you to see how different thread interleavings 
either cause or avoid race conditions. 
See the README for details on how the program works, then answer the questions below.

Then, run it with these arguments (./x86.py -t 1 -p loop.s -i 100 -R dx)

What will %dx be during the run? Use the -c flag to check your answers;
the answers, on the left, show the value of the register (or memory

2. Same code, different flags: (./x86.py -p loop.s -t 2 -i 100

Does the presence of multiple threads affect your calculations? Is

Each thread has its own copy of dx register so when thread 1 starts it doesn't use

No race since no shared ressource.

3. Run this: ./x86.py -p loop.s -t 2 -i 3 -r -R dx -a
dx=3,dx=3 This makes the interrupt interval small/random; use
different seeds (-s) to see different interleavings. 
Does the interrupt frequency change anything?

./x86.py -p loop.s -t 2 -i 3 -r -R dx -a dx=3,dx=3 -s 0 -c
./x86.py -p loop.s -t 2 -i 3 -r -R dx -a dx=3,dx=3 -s 2 -c

Interrupt frequency changes interleaving of executing threads: e.g. first 3 instructions
of thread 1, then 2 from theread 0, then 1 from thread 1 etc., but since at every
context switch the state of the registers (dx) is saved specifically for that thread
and there is no shared ressource, when the thread is allowed resuming it continues
from where it left off.

5. Run with multiple iterations/threads: ./x86.py -p
looping-race-nolock.s -t 2 -a bx=3 -M 2000 
Why does each thread loop three times? 
What is final value of value?

Each thread has its copy of bx initialized at 3 so, since interrupt happens 
by default after 50 instructions, thread 0 completes (when bx decrements 3 times
to reach 0), then thread 1 starts executing with its bx of 3 (also 3 iterations).
So since value is shared, but thread 0 completes before thread 1 starts,
there is no race condition.

6. Run with random interrupt intervals: ./x86.py -p
looping-race-nolock.s -t 2 -M 2000 -i 4 -r -s 0 with
different seeds (-s 1, -s 2, etc.) Can you tell by looking at the
thread interleaving what the final value of value will be? Does the
timing of the interrupt matter? Where can it safely occur? Where
not? In other words, where is the critical section exactly?

./x86.py -p looping-race-nolock.s -t 2 -M 2000 -i 4 -r -s 0
./x86.py -p looping-race-nolock.s -t 2 -M 2000 -i 4 -r -s 1  

Critical section is 1000-1002
1000 mov 2000, %ax
1001 add $1, %ax
1002 mov %ax, 2000

The final value is 2 if each thread is allowed by the interrupt
to complete the 3 instructions of the critical section atomically
so each thread (with 1 loop iteration since bx goes from 0 to -1)
increments shared value.
When a thread is interrupted during execution of critical section
we have race condition and both threads store 1 into value.

7. Now examine fixed interrupt intervals: ./x86.py -p
looping-race-nolock.s -a bx=1 -t 2 -M 2000 -i 1 What
will the final value of the shared variable value be? What about
when you change -i 2, -i 3, etc.? For which interrupt intervals
does the program give the “correct” answer?

When fixed interrupt interval is 1 or 2 the 1st thread to get executed gets
interrupted during critical section (first 3 instructions of the program)
so we have race condition and final value of 1.
When fixed interrupt interval is 3 or greater the 1st thread to get executed 
completes critical section and stores 1 into value,
then 2nd thread loads 1 and increments it to 2 so race condition avoided.

8. Run the same for more loops (e.g., set -a bx=100). 
What interrupt intervals (-i) lead to a correct outcome?
Which intervals are surprising?

Interrupt intervals 1 and 2 have race condition where each thread sabotages the
other one so final value is 100 (same as loop iteration).
Interval 3 and multiples of 3 are correct since we have 3 instructions in critical section,
then 3 instructions for decrementing bx, test and jump so correct final value 200.
Other intervals are surprising since it depends of grouping of instructions
for each thread: 150 for 4, 160 for 5, 157 for 7 etc.

9. One last program: wait-for-me.s. Run: ./x86.py -p
wait-for-me.s -a ax=1,ax=0 -R ax -M 2000 This sets the
%ax register to 1 for thread 0, and 0 for thread 1, and watches %ax
and memory location 2000. How should the code behave? How is
the value at location 2000 being used by the threads? What will its
final value be?

 2000      ax          Thread 0                Thread 1         
    0       1   
    0       1   1000 test $1, %ax
    0       1   1001 je .signaller
    1       1   1006 mov  $1, 2000
    1       1   1007 halt
    1       0   ----- Halt;Switch -----  ----- Halt;Switch -----  
    1       0                            1000 test $1, %ax
    1       0                            1001 je .signaller
    1       0                            1002 mov  2000, %cx
    1       0                            1003 test $1, %cx
    1       0                            1004 jne .waiter
    1       0                            1005 halt

Code first checks if ax is 1.
If true then it jumps to label signaller which stores constant 1 at memory 
address 2000 the halts 
If false it jumps continues with label waiter which starts a loop of loading 
into cx value from memory 2000, check if cx is now 1 and halt only
when it's 1.

The thread 0 is the one responsible to store 1 at address 2000 to signal the 
thread 1 that it can finish the loop, stop waiting.
Thread 1 initialized with ax 0 starts loop, but since it directly finds 1
in memory 2000 halts after only 1 iteration. 

10. Now switch the inputs: ./x86.py -p wait-for-me.s -a
ax=0,ax=1 -R ax -M 2000 How do the threads behave? What
is thread 0 doing? 
How would changing the interrupt interval (e.g., -i 1000, or perhaps 
to use random intervals) change the trace outcome? 
Is the program efficiently using the CPU?

Thread 0 initialized with ax 0 starts loop, keeps checking for 1 at memory 
2000 and gets interrupted after default interval 50, when thread 1 finally stores 
1 at address 2000 and halts, then thread 0 finds 1 and halts.
If we change interrupt interval  (e.g., -i 1000) then thread 0 waits for 1000
instructions for thread 1 to send signal so thread 0 ends the loop.
Thread 0 keeps CPU busy while waiting for signaller. If both threads 
initialize ax to 0 we have infinite loop.
