Homework (Simulation)
This section introduces ssd.py, a simple SSD simulator you can use
to understand better how SSDs work. Read the README for details on
how to run the simulator. It is a long README, so boil a cup of tea (caffeinated
likely necessary), put on your reading glasses, let the cat curl up
on your lap, and get to work.

5. Now, compare performance of the log-structured approach and the
(very bad) direct approach (-T direct instead of -T log). First,
estimate how you think the direct approach will perform, then check
your answer with the -S flag. In general, how much better will the
log-structured approach perform than the direct one?

For every write operation the direct aproach necessitates first a read 
of all the live data in that block, then an erase of the block, 
and then a series of programs to restore all previously live data
as well as write the new data to Flash. 
In general is on the order of # writes.

With log-structured approach we erase once a block then for the next
available pages in the block we can use them for any subsequent writes 
without requiring to read live pages, without erase again and without 
writing again these live pages. 
In general is on the order of 1+(#writes/pages per block)

6. Let us next explore the behavior of the garbage collector. To do
so, we have to set the high (-G) and low (-g) watermarks appropriately.
First, let’s observe what happens when you run a larger
workload to the log-structured SSD but without any garbage collection.
To do this, run with flags -T log -n 1000 (the high watermark default is 10, 
so the GC won’t run in this configuration).
What do you think will happen? Use -C and perhaps -F to see.

The first 128 commands (reads, writes, trims) are succesfull,
but afterwards we have many failures in case of writes because device is full,
since after a trim the page remains in valid state and can't be reused
for a write (should be in Erased state). By default we have 7 blocks
of 10 pages so the 70 spots get filled after 70 writes.

do you think will make for a working system? Use -C and -F to
show the commands and intermediate device states and see.

Better use high watermark  = # of blocks so when the last block starts to

8. One other useful flag is -J, which shows what the collector is doing
when it runs. Run with flags -T log -n 1000 -C -J to see both
the commands and the GC behavior. What do you notice about the
GC? The final effect of GC, of course, is performance. Use -S to
look at final statistics; how many extra reads and writes occur due
to garbage collection? Compare this to the ideal SSD (-T ideal);
how much extra reading, writing, and erasing is there due to the
nature of Flash? Compare it also to the direct approach; in what
way (erases, reads, programs) is the log-structured approach superior?

GC tries to free and erase blocks in sequence, when 7 blocks are in use
it reads live pages in block 0, write them at the end of the log, 
then erases block 0, next time is starts it frees block 1 and so on,
then after block 6 it wraps up back to block 0

Ideal approach doesn't need to erase anything so there are 0 erases
which take most of the time. Also there are also less read and writes
since no need of relocation live data when erasing a block.
Direct approach does a lot of reading, writing and erasing so 6 times
longer than log-structured with Garbage collection.

9. One last aspect to explore is workload skew. Adding skew to the
workload changes writes such that more writes occur to some smaller
fraction of the logical block space. For example, running with -K
80/20 makes 80% of the writes go to 20% of the blocks. Pick some
different skews and perform many randomly-chosen operations (e.g.,
-n 1000), using first -T direct to understand the skew, and then
-T log to see the impact on a log-structured device. What do you
expect will happen? One other small skew control to explore is -k
100; by adding this flag to a skewed workload, the first 100 writes
are not skewed. The idea is to first create a lot of data, but then only
update some of it. What impact might that have upon a garbage
collector?

For direct approach there the skew doesn't change total time since
for each write we need to read live pages, erase block and write old
and new pages.

For log-structured SSD a real workload skew reduces total time (from 126840 to 86400)
since most writes target a few hot pages so the garbage collector has less
reads and writes of live pages to make, since with a skew of 80/20
for 50 logical pages means that 80% of the time 10 logical pages are used
that are spread amongst 7 blocks.
With a skew and skew start after 100 writes, since the skew starts only after
100 writes, not from the beginning it means we have around 100 logical pages
initially, so we increase total time from 86400 to 93920 because in the
beginning there are more reads and re-writes done by garbage collector
since more pages in use, but after skew starts it's similar to skew from
the beginning.
