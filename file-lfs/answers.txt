Homework (Simulation)
This section introduces lfs.py, a simple LFS simulator you can use
to understand better how an LFS-based file system works. Read the
README for details on how to run the simulator.


Questions
1. Run ./lfs.py -n 3, perhaps varying the seed (-s). Can you figure
out which commands were run to generate the final file system
contents? Can you tell which order those commands were issued?
Finally, can you determine the liveness of each block in the final
file system state? Use -o to show which commands were run, and
-c to show the liveness of the final file system state. How much
harder does the task become for you as you increase the number of
commands issued (i.e., change -n 3 to -n 5)?

When we increase the number of operations from 3 to 5, we need to keep
checking the log for new segments between last chunk(imap) and new chunk(imap)
to understand what happened

3. To further test your ability to figure out what updates are made to
disk by each command, run the following: ./lfs.py -o -F -s
100 (and perhaps a few other random seeds). This just shows a
set of commands and does NOT show you the final state of the file
system. Can you reason about what the final state of the file system
must be?

6. Now, let’s do the same thing, but with a single write operation instead
of four. Run ./lfs.py -o -L c,/foo:w,/foo,0,4 to
create file ”/foo” and write 4 blocks with a single write operation.
Compute the liveness again, and check if you are right with -c.
What is the main difference between writing a file all at once (as
we do here) versus doing it one block at a time (as above)? What
does this tell you about the importance of buffering updates in main
memory as the real LFS does?

When writing a file all at once (ascwe do here) we add once all 
data blocks, the updated inode for the file pointing to the data blocks
and final imap chunk poiting to the inode.
When doing it one block at a time (as above) for each append we add
one data block, updated inode poiting to that data blocks, updated
imap chunk poiting to the inode, but since we do it multiple times
only the data blocks remain live while these intermediate inode and 
impa chunk become garbage, only the last ones are live.
It's better to buffer writes in memory to update only once final inode
and imap chunk, save space on disk (shorter log) and avoid garbage
collection work afterwards.

10. LFS makes many different policy decisions. We do not explore
many of them here – perhaps something left for the future – but here
is a simple one we do explore: the choice of inode number. First, run
./lfs.py -p c100 -n 10 -o -a s to show the usual behavior
with the ”sequential” allocation policy, which tries to use free
inode numbers nearest to zero. Then, change to a ”random” policy
by running ./lfs.py -p c100 -n 10 -o -a r (the -p c100
flag ensures 100 percent of the random operations are file creations).
What on-disk differences does a random policy versus a sequential
policy result in? What does this say about the importance of choosing
inode numbers in a real LFS?

The sequential policy tries to use free inode numbers nearest to zero
so for 10 file creations uses only 1st slot of checkpoint region and 
adds after each file creation 1 updated chunk imap (which has space
for 16 inodes 0-15). In the end we use 43 blocks.
The random policy assigns random inode number from 1 to 255 (0 taken by /)
so for 10 file creations we use many slots of checkpoint region and 
add after each file creation 2 updated chunk imap blocks (each with 
space for 16 inodes). In the end we use 53 blocks


11. One last thing we’ve been assuming is that the LFS simulator always
updates the checkpoint region after each update. In the real
LFS, that isn’t the case: it is updated periodically to avoid long
seeks. Run ./lfs.py -N -i -o -s 1000 to see some operations
and the intermediate and final states of the file system when
the checkpoint region isn’t forced to disk. What would happen if
the checkpoint region is never updated? What if it is updated periodically?
Could you figure out how to recover the file system to the
latest state by rolling forward in the log?

If the checkpoint region is never updated we don't know which blocks
are live and which garbage, whick blocks latest valid imap chunks, 
we don't know where to look for data and metadata, where to start.
If the checkpoint region is updated periodically we know where to start
looking and avoid long seeks if it were done after each update.
We can recover the file system to the latest state by rolling forward in 
the log, but it takes a lot of steps and analysis:
- we know that first 4 blocks contain checkpoint region, initial data 
block for /, initial inode for /, initial chunk imap for /
- keep detecting a new chunk(imap) block and analyse blocks between
these consecutive chunk(imap) blocks to detect what operation must have
taken place. We update checkpoint region contents based on inode numbers
and address of latest chunk(imap).
-when we can't detect operation between consecutive chunk(imap)
it means we found garbage after previous chunk(imap). 
The trouble is if it seems valid operation altough based on garbage blocks.
