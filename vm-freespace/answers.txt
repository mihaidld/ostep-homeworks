2. How are the results different when using a WORST fit policy to
search the free list (-p WORST)? What changes?
With BEST fit policy we search full list (O(n)) to find smallest size that
fits request+header, with WORST we still search full list (O(n)) to find
largest size free segment. Since we choose every time largest segment
we keep in free list only larger segments and avoid accumulating small 
unusable ones  (like with BEST fit), but if we ever need a larger one 
of 100 later we can not accomodate this request altough we have many 90
segments.

./malloc.py -n 10 -H 0 -p WORST -s 0 -c

Free List [ Size 5 ]: [ addr:1000 sz:3 ][ addr:1003 sz:5 ]
[ addr:1008 sz:8 ][ addr:1016 sz:8 ][ addr:1033 sz:67 ]

After 10 operations free list since we dont reuse freed segments and only
remove chunks from larger segment we have longer list (5 vs 4 for BEST)
with size of largest (67 vs 84 for BEST)

4. For the above questions, how the list is kept ordered can affect the
time it takes to find a free location for some of the policies. 
Use the different free list orderings (-l ADDRSORT, -l SIZESORT+,
-l SIZESORT-) to see how the policies and the list orderings interact.

With ADDRSORT: whenever a segment is freed, it is inserted in the free list
based on its address to keep list sorted by address O(n)
Combined with BEST or FIRST fit it's going to allocate mostly from beginning of list
(smaller addresses). Combined with WORST it's going to allocate mostly from
end of list (larger segments).

With SIZESORT+: whenever a segment is freed, it is inserted in the free 
list based on its size to keep list sorted by size increasingly O(n)
Combined with BEST we increase efficiency since we can stop searching after
find 1st fit (like FIRST), we don't need to keep looking till the end.
Combined with WORST, it still is O(n) since we need to find last segment
in list when allocating.

With SIZESORT-: whenever a segment is freed, it is inserted in the free 
list based on its size to keep list sorted by size decreasingly O(n)
Combined with WORST we increase efficiency since we can stop searching after 
1st segment (like FIRST, either fit or not sufficient space), we don't need 
to keep looking till the end. Combined with BEST, it still is O(n) since 
we need to find last segment in list when allocating.

5. Coalescing of a free list can be quite important. Increase the number
of random allocations (say to -n 1000). What happens to larger
allocation requests over time? Run with and without coalescing
(i.e., without and with the -C flag). 
What differences in outcome do you see? How big is the free list over time 
in each case? 
Does the ordering of the list matter in this case?

Without coalescing, list gets fragmented over time and contains contiguous
free segments that can't accomodate larger accomodation requests.
e.g.
./malloc.py -n 1000 -H 0 -p FIRST -s 0 -c
Without coalesce after 1000 operations list has size 51 and contains many 
small segments, with coalesce size 1 with large segments. With SIZESORT+ 
we get same result as with BEST (doesn't matter sorting) size 31 

./malloc.py -n 1000 -H 0 -p BEST -s 0 -c 
size 31 after 1000 operations. Less fragmented than FIRST since we found
bets fit, but more expensive during each allocation.

./malloc.py -n 1000 -H 0 -p WORST -s 0 -c
size 100 after 1000 operations containg only segments of 1, and many requests
not allocated since the largest chunk kept splitting. WORST needs to be combined 
with coalescing, even with SIZESORT- we still get fragmentation and unfulfilled
allocation requests
