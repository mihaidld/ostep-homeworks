3. Now let’s look at main-deadlock.c. Examine the code. This
code has a problem known as deadlock (which we discuss in much
more depth in a forthcoming chapter). 
Can you see what problem it might have?

Deadlock with mutex locks occurs when threads acquire locks in different orders, creating circular dependencies. 
Thread1 (worker with argument 0) acquires mutex m1 and then tries to acquire mutex m2
Thread2 (worker with argument 1) acquires mutex m2 and then tries to acquire mutex m1
Both threads become permanently blocked, waiting for each other to release their held resources.

6. Let’s next look at main-signal.c. This code uses a variable (done)
to signal that the child is done and that the parent can now continue.
Why is this code inefficient? 
(what does the parent end up spending its time doing, 
particularly if the child thread takes a long time to complete?)

If the parent gets execution for a while before child it uses CPU time
in a loop, then eventually is deschedueled, child sets done to 1
so parent exits loop and completes.
If child gets executed before loop in parent it sets done to 1
so parent finishes without loop.
Code inefficient since we don't enough for sure that child will
get executed first to avoid waste CPU time by parent.

8. Now look at a slightly modified version of the code, which is found
in main-signal-cv.c. This version uses a condition variable to
do the signaling (and associated lock). Why is this code preferred
to the previous version? Is it correctness, or performance, or both?

This code is preferred because of correctness (uses signaller-wait with a pthread condition variable)
and performance since, if the parent gets executed first it acquires the lock,
finds value 0 for done so it makes the wait call, which, in addition to putting the calling 
thread (main) to sleep, it releases the lock when putting said caller to sleep. So only
one loop iteration was executed then execution can pass to child which acquires released lock
sets sone to 1 and signals, then releases lock. So parent is awaken, finds done 1 and ends loop.
No more CPU waste time if parent gets executed first.
